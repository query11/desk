# Desk 补充优化实施提示词

请在当前仓库中实施下面的补充优化，完成代码修改、必要的回归测试和结果说明。本文与 [第一份优化提示词](OPTIMIZATION_PROMPT.md) 配套：先处理异常恢复、点击穿透和开机自启，再处理资源清理与日志诊断。

## 开始前

- 阅读 `README.md`、`docs/TESTING.md`、`.github/workflows/build.yml`、第一份优化提示词和适用的 `AGENTS.md`，检查当前分支、工作区修改和已有实现。
- 第一轮可能已经修改注入状态机、宿主与引擎通信、资源缓存和设置结构。复用这些实现，保持协议和资源所有权一致，避免再建立一套独立机制。
- 使用现有检出目录；云任务已经隔离，除非用户明确要求，不创建额外 worktree。保留已有工作，按具体功能组织便于审阅的修改与提交。
- 以下 Windows 问题来自静态调用链审查，实施前先核对当前代码和触发条件。日志问题已通过直接运行原始 C# 日志代码复现：运行期间超过 2 MiB 没有轮转，下一次初始化直接删除超限日志。线程状态存在清理缺口，但尚未实测长期内存增长。
- 本轮必须完成第 1～5 项；文末的两项功能扩展属于后续候选，不默认纳入本轮。

## 1. 宿主异常退出后的自动还原与紧急恢复

重点文件：

- `src/Desk/Program.cs`、`src/Desk/DeskApp.cs`、`src/Desk/AutoHideController.cs`、`src/Desk/RuntimeWriter.cs`。
- `src/DeskTap/src/config.cpp`、`src/DeskTap/src/engine.cpp`、`src/DeskTap/src/clickthrough.cpp`、`src/DeskTap/src/monitor.cpp`。

### 问题

目前还原主要依赖 `DeskApp.ExitThreadCore()` 写入停用配置并恢复自动隐藏设置。宿主崩溃或被强制结束时，这条路径不会运行；引擎仅监听配置文件变化，可能继续使用最后一份启用配置。快捷键和托盘也随宿主消失。

`AutoHideController` 保存的原始自动隐藏状态仅在宿主内存中。异常退出后，这个状态丢失，后续启动不能可靠区分用户原本开启的自动隐藏和 Desk 临时开启的自动隐藏。

### 修改要求

- 复用第一轮的状态协议，增加宿主存活与控制权归属信息。识别进程实例和会话，防止 PID 复用、旧配置或旧监控任务影响新宿主。
- 选择适合当前权限环境的存活检测方式，兼顾开始菜单 AppContainer。不能把访问被拒绝、一次超时、休眠或短暂调度停顿直接认定为宿主死亡；如果使用超时，明确时钟、宽限期和恢复策略。
- 确认宿主失效后，在各自所属 UI 线程恢复 Desk 修改的属性、窗口主题和点击区域，移除信息岛并停止不必要的后台工作。引擎进入可重新连接的停用状态，不要求强行卸载已固定在系统进程内的 DLL。
- 自动隐藏等系统设置应在修改前保存必要的恢复信息，并记录 Desk 实际修改了什么。恢复时检查当前状态及归属，避免覆盖用户后续主动修改的设置。普通还原、异常恢复和重新启动应使用同一套规则。
- 处理新旧宿主交接：旧监控回调不得撤销新宿主已经接管并应用的配置；宿主恢复后不能自动循环重启资源管理器。
- 提供独立于设置窗口的紧急恢复入口，例如 `Desk.exe --restore`。明确正常宿主存在、宿主卡住、没有宿主和旧引擎仍在运行时的行为，不能因单实例逻辑直接退出而不执行恢复。

### 验收

- 在独立 Windows 测试环境中强制结束 `Desk.exe`，确认美化和点击区域在约定时间内恢复，信息岛停止工作。
- 分别测试用户原本开启/关闭自动隐藏、Desk 临时强制自动隐藏，以及用户在运行中修改系统设置的情况。
- 覆盖宿主快速重启、目标进程重启、旧回调延迟到达、休眠恢复和无法读取存活状态。结果不应被过期信息反复覆盖。
- 紧急恢复入口在设置窗口打不开时仍然可用；重复执行不会破坏已经恢复的状态。

## 2. 点击穿透的关闭与任务栏重建必须可靠

重点文件：`src/DeskTap/src/clickthrough.cpp`、`src/DeskTap/src/engine.cpp`、`src/DeskTap/src/winutil.cpp`。

### 问题

`OnElementAdded` 会直接将最新配置写入 `t_enabled`。如果关闭穿透的配置已经发布，但重应用回调尚未执行，此时新增元素回调可能先把 `t_enabled` 改为 `false`。之后 `OnConfigApplied(false)` 看到 `wasEnabled == false`，跳过 `ClearRegions()`，之前应用的窗口裁切可能残留。

此外，同一 XamlRoot 内替换 TaskbarFrame 时，代码更新了 Frame 的弱引用，却仅在 `layoutRevoker` 为空时订阅布局事件，可能继续监听旧 Frame。

### 修改要求

- 将关闭穿透做成幂等操作：根据实际保留的 Desk 窗口区域记录清理，不仅依赖某个布尔值从真变假的瞬间。重复关闭、全局停用、正常退出和异常恢复都应有效。
- 保持窗口和区域的所有权检查；窗口已销毁、句柄已复用或区域被其他代码改动时，不应盲目恢复。核对当前的区域比较是否足以识别 Desk 应负责清理的区域。
- TaskbarFrame 替换时撤销旧布局订阅、绑定新 Frame。处理 XamlRoot 变化、显示器移除以及重复元素通知，避免遗留订阅和过期 HWND。
- 核对 XAML 回调与窗口 subclass 的线程归属。跨线程时通过明确的状态和所属 dispatcher 处理，不能假定不同线程访问同一份 `thread_local` 状态。

### 验收

- 覆盖“发布关闭配置→先收到新元素回调→再执行重应用”的顺序，以及多次重复关闭、重新开启和全局停用。
- 开启穿透后改变缩放、切换自动隐藏、插拔副屏或重建任务栏，检查裁切和实际布局保持一致。
- 替换 Frame 后，新 Frame 的布局变化能够继续更新点击区域；旧 Frame 的回调不再参与更新。
- 停用后原生任务栏、托盘弹窗和空白区域恢复正常交互。

## 3. 开机自启操作结果与界面状态保持一致

重点文件：`src/Desk/Autostart.cs`、`src/Desk/DeskApp.Api.cs`、`src/Desk/Ui/Pages/SettingsPage.xaml.cs`。

### 问题

关闭自启时忽略了删除计划任务的退出码，删除备用注册表项失败也只写日志，随后仍设置 `IsEnabled = false`。启用时，备用注册表项写入失败也可能最终设置 `IsEnabled = true`。当前任务查询主要检查任务是否存在，不能充分证明它已启用且指向正确的程序。

### 修改要求

- 将计划任务和注册表操作改为有明确结果、错误原因的操作。区分成功、已达到目标状态、失败和无法确认，不能只更新内存中的布尔值。
- 修改后核对实际状态；关闭需确认两种启动来源均已移除或关闭，启用需确认至少一个有效来源可用。区分“任务不存在”和“查询失败”，检查任务启用状态及启动目标。
- 保留计划任务优先、注册表备用的现有策略；失败回退也必须验证成功。失败时显示可理解的错误和实际状态，不输出“已开启/已关闭”的假成功日志。
- 异步调用应正确传递操作结果和异常，避免 continuation 隐藏失败。界面操作完成后刷新真实状态，并妥善处理启动时后台刷新与用户操作的交错。
- 保持慢操作在后台执行，限制等待时间，避免用户界面卡住。

### 验收

- 模拟计划任务创建、删除、查询失败，以及注册表写入、删除失败。界面、日志和返回结果应一致。
- 测试计划任务已存在但被禁用、任务指向旧路径，以及计划任务与注册表项同时存在的情况。
- 暂时性故障解除后重新操作能够成功；程序重启和实际登录后的行为与界面显示一致。

## 4. 补齐线程与长期运行资源的清理

重点文件：`src/DeskTap/src/engine.cpp`、`src/DeskTap/src/monitor.cpp`、`src/DeskTap/src/watcher.cpp`、`src/DeskTap/src/clickthrough.cpp`，以及第一轮新增的渲染缓存。

### 问题

引擎和信息岛通过 `thread_local` 裸指针保存 `new` 出来的线程状态，缺少对应的退出清理。全局线程列表保留 dispatcher，投递失败也不移除。信息岛状态持有计时器、控件和画刷；线程退出或任务栏重建时可能遗留资源。

### 修改要求

- 明确每类状态、订阅、计时器、窗口 subclass、dispatcher 和缓存的所有者，以及退出时的释放顺序。
- 尽可能在 dispatcher 关闭、COM/XAML 上下文仍有效时，在所属线程完成解绑、停止和释放。不能只把裸指针机械替换为自动析构对象，再在错误线程或 DLL loader lock 中释放 XAML 资源。
- 清理失效线程的全局登记；检查 `TryEnqueue` 等投递结果，避免已关闭 dispatcher 和待执行标志长期残留。旧回调通过生命周期标记或等效机制失效，不能访问已释放状态。
- 与第一轮效果缓存共享生命周期设计，保持进程级必要资源与线程级资源的边界，避免重复清理、死锁或缓存无限增长。

### 验收

- 增加仅用于诊断的必要计数，观察已登记线程、计时器、订阅和缓存项的创建与释放。
- 重复创建/销毁任务栏相关对象、连接/移除显示器、打开/关闭设置及信息岛，确认已失效资源得到回收。
- 在确实发生 XAML 线程退出与重建的场景下验证清理；单纯重复开关控件不能代替线程生命周期测试。
- 记录预热后的长期内存和句柄趋势，结合 Desk 自身计数判断，不把资源管理器其他组件的波动直接归因于 Desk。

## 5. 日志轮转与一键诊断导出

重点文件：`src/Desk/Log.cs`、`src/DeskTap/src/log.cpp`、`src/Desk/DeskApp.Api.cs`、`src/Desk/Ui/Pages/SettingsPage.xaml` 及其代码文件。

### 问题

目前日志主要在初始化时检查 2 MiB 上限，运行期间持续追加。重新启动时超限日志会被直接删除，可能恰好丢失上一轮故障的证据。原生日志也需要核对并采用一致的保留策略。

### 修改要求

- 按写入量在运行期间轮转，限制单文件大小和保留总量，保留最近几份历史日志。启动时不直接丢弃全部上一轮故障记录。
- 正确处理并发写入、轮转、不同进程写日志及磁盘操作失败；日志异常不能导致宿主或被注入的进程崩溃。
- 减少高频重复日志和对 UI 线程的同步磁盘压力。若引入缓冲或后台队列，队列必须有界，并说明错误记录和退出时刷新的策略。
- 在设置页面提供“一键导出诊断”，保存到用户选择的位置。包含 Desk/引擎版本、Windows 构建号、显示器与缩放信息、主题标识、当前引擎状态、最近错误和选定的 Desk 日志。
- 导出范围限定为诊断所需的数据，不整份打包用户目录、进程环境或任意文件。可对用户名等本地路径信息做替换，保留分析故障所需的相对路径。
- 导出过程在后台执行，有完成或失败提示。源日志正在写入、某份日志暂不可读时，结果中明确说明缺失部分。

### 验收

- 使用隔离临时目录和实际日志实现验证：持续写入超过阈值后发生轮转，保留范围内的新旧记录可找到，总量受限，重新启动不丢失全部历史。
- 覆盖并发写入、不可写目录和轮转失败，确认应用主流程仍可运行。
- 实际打开导出的诊断包，核对内容与当前会话一致，并确认能够区分宿主和各目标进程的日志。

## 验证与交付

- 为恢复状态机、事件顺序、操作失败结果、日志保留规则等编写能发现原问题的测试，优先通过最小的可替换边界模拟故障。测试应调用实际生产逻辑，不另写一份同样的实现。
- 根据第一份提示词和现有 CI 执行 C# 还原、构建、发布与 Windows 原生 DLL 构建；检查修改对旧配置、旧引擎和正常退出还原的兼容性。
- 在 `docs/TESTING.md` 增加本轮故障恢复及长期运行场景，明确可重复执行的步骤和预期结果。涉及强制结束进程、任务栏重建等场景时使用独立 Windows 测试环境。
- Linux 上能执行的检查应实际完成；Windows 桌面行为、原生资源生命周期和性能需单独验收。环境不具备对应能力时，报告未运行项和具体操作步骤，不用交叉编译通过替代运行结果。
- 最终按五项说明改动、设计取舍、测试结果和剩余限制。故障恢复时间、内存趋势与性能收益只引用实际测量；尚未实测的部分明确标注。

## 后续功能候选：另行安排，不默认实施

### 每个显示器独立的最大化策略

当前 `WindowMonitor` 主要判断主任务栏所在显示器。后续可为每个显示器分别决定浮岛、整条任务栏或自动隐藏行为，核对系统接口是否支持相应粒度，不能把系统级开关包装成每屏独立能力。需要覆盖不同 DPI、主副屏切换、热插拔、跨屏窗口和虚拟桌面。

### 主题预览与自动回退

后续可增加有倒计时的主题预览，用户确认后才持久保存；超时、取消、关闭窗口或预览应用失败时恢复上一份已确认配置。与按主题参数存储及宿主异常恢复共享事务归属，避免一次预览覆盖用户其他主题的配置。验收应包含快速连续预览、应用失败和宿主在预览期间退出。
